```swift
func voteShare(shareId: Int64, voteType: Int) async throws {
    let data = try await OTONetwork.request(
        .voteShare(shareId: shareId, voteType: voteType)
    )

    let decoder = JSONDecoder()
    let response = try decoder.decode(OTOResponseModel<EmptyData>.self, from: data)

    guard response.respCode == 0 else {
        throw NSError(
            domain: "ShareService",
            code: response.respCode,
            userInfo: [NSLocalizedDescriptionKey: response.respMsg ?? "投票失败"]
        )
    }
}
```

### 3. 核心业务逻辑

#### 3.1 VoteState 枚举
**文件**: `guanzhi/View/SharePages/ShareInteractionViewModel.swift`

**设计亮点**:
```swift
enum VoteState: Int, Codable {
    case none    = -1  // 取消/默认状态
    case neutral = 0   // 无感（预留）
    case agree   = 1   // 赞同

    func toggled(to target: VoteState) -> VoteState {
        return self == target ? .none : target
    }
}
```
- ✅ 使用枚举强制三态互斥（编译期保证）
- ✅ rawValue 对应后端 voteType

#### 3.2 ShareInteractionViewModel
**文件**: `guanzhi/View/SharePages/ShareInteractionViewModel.swift`

2. **竞态保护**:

```swift
private var operationId: Int = 0  // ✅ 全局唯一

func vote(to targetState: VoteState) {
    operationId += 1
    let currentOp = operationId

    // ... 网络请求 ...

    guard currentOp == self.operationId else {
        return  // 丢弃过期响应
    }
}
```

3. **失败回滚**:
```swift
catch {
    guard currentOp == self.operationId else { return }

    await self.rollback(to: oldState)
    self.errorMessage = "操作失败，请重试"
}
```

4. **状态初始化**:

```swift
func initialize(share: Share, onStateChanged: ((Int64, VoteState, Int, Int) -> Void)? = nil) {
    self.currentShareId = share.id
    self.agreeCount = share.agreeCount
    self.voteState = VoteState(rawValue: share.currentUserVoteType ?? -1) ?? .none

    // 保存原始值用于回滚

    self.originalAgreeCount = self.agreeCount
}
```

## 🛠 技术亮点

### 1. 三态互斥设计
- **问题**: 原始设计使用 `isLiked: Bool` 和 `isDisliked: Bool` 可能同时为 true
- **解决**: 使用 `VoteState` 枚举，编译器在编译期强制唯一性
- **来源**: GPT 专家审查建议

### 2. 全局 operationId
- **问题**: 每个按钮独立的 operationId 会导致跨操作竞态
- **解决**: 点赞、无感、取消共用一个全局递增的 operationId
- **场景**: 用户快速切换 "点赞 → 无感"，响应乱序返回时仍能保证最终状态正确
- **来源**: GPT 专家审查建议

### 3. 双向数据流
```
ShareDetailView (父)
    ↓ share (向下传递)
InteractionOverlayView
    ↓ share
ShareInteractionViewModel (业务逻辑)
    ↑ onVoteStateChanged (向上通知)
InteractionOverlayView
    ↑ onVoteStateChanged
ShareDetailView (更新 selectedShare)
```

### 4. 乐观更新 + 失败回滚
- 立即响应（< 16ms）
- 后台同步（100-500ms）
- 失败时自动回滚
- 用户体验接近 Instagram/微信

## 📝 关键决策记录

### 决策 1: 使用乐观更新而非同步等待
- **理由**: 用户体验优先，避免网络延迟造成的卡顿感
- **权衡**: 需要处理失败回滚，增加代码复杂度
- **参考**: Instagram、微信等主流应用的实践

### 决策 2: VoteState 枚举设计
- **理由**: 编译期保证状态唯一性，避免运行时 bug
- **来源**: GPT 专家审查指出的设计缺陷
- **影响**: 代码更健壮，但需要额外的状态转换逻辑

### 决策 3: 全局 operationId
- **理由**: 防止跨操作竞态（点赞 → 无感切换场景）
- **来源**: GPT 专家审查的关键修复
- **影响**: 所有投票操作共享一个序列，确保顺序一致性

### 决策 4: 预留无感功能但不显示 UI
- **理由**: 后端已支持，前端预留逻辑便于未来启用
- **产品要求**: 当前版本只显示点赞按钮
- **实现**: ViewModel 支持完整逻辑，UI 仅注释掉无感按钮
