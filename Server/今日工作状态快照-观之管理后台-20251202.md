### 1.1 Phase 2: 后端数据库 Schema 修改

#### 1.1.1 新增 tag_type 字段

**问题背景**:
- 原需求：标签需要区分"正面"和"负面"类型
- 原方案讨论：是新增 tag_key 字段还是复用现有 tag_code？
- 最终决策：复用 tag_code（已是拼音），新增 tag_type 字段标识类型

**执行的迁移SQL**:

**文件**: `/Server/onettoo/src/main/resources/sql/migration-add-tag-type.sql`

```sql
-- 为 tag_definition 表添加 tag_type 字段
ALTER TABLE tag_definition
ADD COLUMN tag_type VARCHAR(20) DEFAULT 'NEGATIVE'
COMMENT '标签类型: POSITIVE(正面), NEGATIVE(负面)'
AFTER tag_name;

-- 将所有现有标签设置为 NEGATIVE
UPDATE tag_definition SET tag_type = 'NEGATIVE' WHERE tag_type IS NULL;
```

**执行方式**:
```bash
/opt/homebrew/Cellar/mysql/9.5.0_2/bin/mysql -u root ONETTOO < \
  /Users/zaptain/Library/Mobile\ Documents/com~apple~CloudDocs/DarkForce/Seee/guanzhi/Server/onettoo/src/main/resources/sql/migration-add-tag-type.sql
```

**结果**:
- ✅ tag_definition 表新增 tag_type 字段 (VARCHAR(20), DEFAULT 'NEGATIVE')
- ✅ 所有现有标签（8条本地测试数据）默认设置为 NEGATIVE

#### 1.3.5 创建 Schema 兼容的导入 SQL

**问题分析**:

AWS导出的SQL直接导入会有问题：
1. AWS的 `tag_definition` 表**缺少** `tag_type` 字段（本地新增的）
2. 如果使用 `DROP TABLE` 会丢失本地的 `tag_type` 列定义
3. 需要手动适配 schema 差异

**解决方案**:

创建自定义导入SQL: `aws_config_import_fixed.sql`

**文件**: `~/Desktop/local_backup_20251202/aws_config_import_fixed.sql`

**关键修改**:

```sql
-- 不使用 DROP TABLE，改用 TRUNCATE（保留表结构）
SET FOREIGN_KEY_CHECKS=0;

TRUNCATE TABLE tag_definition;
TRUNCATE TABLE fade_config;
TRUNCATE TABLE points_rule;
TRUNCATE TABLE level_definition;

-- 明确指定列名，为 tag_type 字段提供默认值
INSERT INTO tag_definition (id, tag_code, tag_name, tag_type, min_level_code, is_active, sort_order)
VALUES
(1,'MIJING','秘境','NEGATIVE','SHUIMU',1,0),
(2,'ZHENXIU','珍馐','NEGATIVE','LANDONG',1,0),
(3,'WANQU','玩趣','NEGATIVE','LANDONG',1,0),
(4,'CAIKENG','踩坑预警','NEGATIVE','LANDONG',1,0),
(5,'MAOMAO','猫猫出没','NEGATIVE','LANDONG',1,0),
(6,'CHAOSHENG','朝圣','NEGATIVE','SHUIMU',1,0),
(7,'RICHU','日出','NEGATIVE','LANDONG',1,0),
(8,'JISHI','集市','NEGATIVE','LANDONG',1,0);

-- 其他表的导入语句（fade_config, points_rule, level_definition）
-- 这些表没有schema差异，直接使用AWS原始数据
```

**核心处理**:
- ✅ 使用 `TRUNCATE` 清空数据，保留表结构
- ✅ 明确列名，避免字段顺序问题
- ✅ 为所有标签补充 `tag_type='NEGATIVE'` 默认值
- ✅ 其他3张表没有schema差异，直接导入

## 附录 B: 关键决策记录

**决策1: tag_type 字段放在 tag_definition 表而非新建映射表**

**原因**:
- 标签类型是标签的固有属性，不会频繁变化
- 避免join查询，提升性能
- 简化前端逻辑

**决策2: 修复 FadeConfig 硬编码而非继续使用**

**原因**:
- 硬编码违反"以后端为准"的架构原则
- AWS和本地数据库id可能不一致，导致保存失败
- 与其他配置接口保持一致性

**决策3: 完全重写 TagsConfig 和 LevelsConfig 而非小修小补**

**原因**:
- 字段变化较大，小修改容易遗漏
- 重写可以优化代码结构
- 确保与后端完全对齐

**决策4: 使用 TRUNCATE 而非 DROP TABLE 导入AWS数据**

**原因**:
- 保留本地表结构（tag_type 字段）
- 只清空数据，不改schema
- 避免触发器和约束丢失
